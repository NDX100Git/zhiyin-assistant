# 一万单排队下的读取容量（2026-10-19 14:09）

- 结论：**通过**
- 判定线（本轮硬指标）：一万单排队、单进程、并发 16 时 QPS 不低于 200，且各档 p95 低于 1000 ms
- 实测：并发 16 时 **243.5 次/秒**，p95 92 ms，对 200 的余量 +21.8%
- 各档峰值：247.1 次/秒（并发 64）
- 被测服务进程数：**单进程（启动时不加 --workers）**
- 背景口径（不作判定线）：10000 人同时在线、每 30 秒轮询一次 = 333.3 次/秒，峰值 247.1 次/秒对它的余量 -25.9%
- 读取容量随在途排队订单数变化；本结果对应上面的排队规模，换规模要重跑。

## 补充说明

- 单进程：启动不加 --workers，全程只有一个 uvicorn 进程（采样 pid 见上）。
- 基线对照：同一工作树、同一压测库、同样 skip-fill 口径，改动前（0f5d826）并发 16 是 280.8 次/秒、p95 80 ms；改动后两次读数为 266.2 / 246.6 次/秒、p95 84 / 89 ms，差异在 ±10% 的机器噪声内，本轮没有把整机 QPS 往上推（原因见下一条）。
- 每请求 CPU 现状：3.5-4.3 ms，分布见「每请求 CPU 分解」：鉴权 0.55、count(*) 0.54、一页 20 单 ORM 0.68、待确认换文件 0.37、文件清单 0.41、框架与线程池 1.1-1.9，队列快照命中 0.008。
- 本轮改的是队列快照重建（一万单 11.4 ms -> 8.8 ms CPU），它只占单请求 0.9%，所以端到端读数不动；要再往上走必须动 app/services/order_service.py 与 app/utils/security.py（不在本单文件边界内），见结果汇总。

## 口径

- 每个档位用固定并发持续打 `/api/order/list`，按成功响应数除以实际测量时长算 QPS。
- 失败计入失败次数，不计入 QPS；失败样本会打印在终端。
- 每请求 CPU = 被测进程 `/proc/<pid>/stat` 的 utime+stime 增量除以成功次数；折合核数 = CPU 增量除以墙钟时长，单进程超过 1.0 核说明这一档已经打满一个核。
- 一万人每 30 秒一次摊平成均匀流量是「整套服务」的容量口径；真实流量是脉冲式，瞬时峰值会更高，需要多实例时另算。单进程目标是 200 次/秒，留出多实例叠加的余量。
