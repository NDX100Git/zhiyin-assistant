# 浏览器端到端回归

一条命令跑学生端与老师端的完整闭环，两个视口各跑一遍。每个视口按顺序跑三段：

**单文件闭环**

- 学生：登录 → 上传 PDF → 跳过 AI 直接下单 → 模拟支付 → 我的订单 → 订单详情 → 换文件（待老师确认）
- 老师：登录 → 队列看到待确认 → 确认换文件 → 下载并确认看到 → 开始打印 → 打印完成 → 核销
- 学生：订单详情看到已完成

**多文件闭环**

- 学生：一次选两份 PDF 合成一单 → 下单支付 → 进详情 → 换第二份（先选换哪一份）→ 提交待老师确认
- 老师：队列看到两份文件名 → 确认弹窗点名第 2 份 → 通过 → 逐份下载
- 断言：点第二份下载时接口参数是 `file_index=2`、返回的文件名是第二份、打开的链接就是这一份的签名链接；下载第一份也必须拿到第一份
- 学生：详情按序号列出两份，第二份为提交后的版本、第一份保持不变

**四文件闭环**

- 学生：一次选四份 PDF 下单支付
- 桌面：文件列只展开前三份，点「查看全部 4 个文件」打开弹窗，四份逐条列出且各自有下载按钮，逐份点下载都对上自己的序号
- 手机：卡片逐份列出四份，下载按钮不小于 44 像素，390 宽无横向溢出

**队列条数与封顶**

- 只拉一屏时，提示里的「还有 N 单未显示」与页面自己的账（接口 `total` − 已列出条数）对得上
- 点过「加载更多」之后，连续两拍 5 秒轮询都按已加载条数（120）拉，列表条数不缩水、桌面视口勾上的行不丢（看页面真实请求的 `page_size`，不看文案），不再回落到第一屏 60 条
- 点过「加载更多」之后再执行一次订单动作（点「开始打印」）——动作之后那条刷新、以及随后连续两拍 5 秒轮询，仍然按已加载条数（120）拉：列表条数既不缩水也不改成别的数、勾选不丢、请求条数不回落到 60 条（旧实现里动作走全量刷新，会把增量清零，下一拍就只剩 60 条）
- 真的造出超过 200 单（调学生端下单接口批量下单，复用回归里刚上传的文件），断言页面按 200 条渲染、提示写「已显示前 200 单 … 还有 N 单未显示」、「加载更多」按钮消失

**生产构建的接口地址**

- 学生端与老师端各用 `.env.production` 打一次生产包（构建时把 `VITE_API_BASE_URL` 从环境里摘掉）
- 扫描产物里有没有 `127.0.0.1`、`[::1]`、`localhost:端口`、`192.168/10./172.16-31` 这类本机与内网地址
- 老师端额外校验 `.env.production` 里必须有 `VITE_API_BASE_URL` 且留空（同源相对路径）

**学生端自带 AI 密钥（依赖另一路界面）**

- 「我的」页打开 AI 密钥面板 → 填无效密钥 → 测试连通给出可读原因 → 清除后回到「学校共享」
- 密钥只出现在请求头里：先把密钥「保存」进本机存储，再点「测试连通」逼出一次真实 AI 请求
  （`POST /api/ai/key-check`）——面板的「保存」只写本机存储、一个请求都不发，光保存抓不到请求头；
  保存后输入框会被清空，「测试连通」只能取本机存着的那把，所以断言的是「保存已生效」而不是「输入框的值被带出去」
- 断言：这次请求的 `X-LLM-Api-Key` 请求头等于刚保存的密钥；本步所有请求的 URL 参数与请求体、
  页面地址、页面可见文本里都没有密钥明文（面板只显示前四位与后四位）；收尾点「清除并改用学校共享」，
  并确认本机存储与页面文本里都不再留着这把密钥
- 面板不在本分支时这两步**显式跳过并标注依赖**（终端与 `result.json` 都写原因），不写成恒真断言

视口固定为 **390×844**（手机，双倍像素密度）与 **1440×900**（桌面）。390 下额外检查老师端队列、确认弹窗与多文件卡片无横向溢出、按钮不小于 44 像素。

## 跑法

```bash
# 首次运行：三处依赖都要装
cd student-app && npm install
cd ../teacher-web && npm install
cd ../e2e && npm install

node run.mjs --start
```

`--start` 会做四件事：

1. 重建独立库 `zhiyin_e2e`（库名不以 `_e2e` 结尾会拒绝），对象存储桶用 `zhiyin-files-e2e`；
2. 起后端（默认 `http://127.0.0.1:8100`）；
3. 起学生端 H5（默认 `http://127.0.0.1:3100`）与老师端（默认 `http://127.0.0.1:3101`）；
4. 跑完自动停掉三个服务。

也可以对着已经起好的开发环境跑：

```bash
node run.mjs
```

默认连 `5173`（学生端）、`5174`（老师端）、`8000`（后端）；用 `--student-url`、`--teacher-url`、`--backend-url` 覆盖。

老师账号默认从 `backend/.env` 的 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 读取，也可以用 `E2E_ADMIN_USERNAME` / `E2E_ADMIN_PASSWORD` 覆盖。Python 解释器按 `E2E_PYTHON` → `Temp/zhiyin-venv` → `backend/.venv` → `python3` 的顺序探测。

调试时可以加 `E2E_TRACE=1`，会额外打印老师端队列按钮的匹配结果与 `/api/admin/*` 请求。

## 失败怎么读

每一步都会打印序号、名称与耗时。失败时终端给出：

```
失败：视口 390 卡在第 15 步「老师下载新文件并确认看到」
原因：...
现场：e2e/artifacts/<时间>/
```

现场目录里有失败页截图、页面正文、三个服务的日志与 `result.json`。接口 4xx/5xx 与页面未捕获异常也会在最后的「页面错误汇总」里点名。

## 常见问题

- 启动报找不到 Chrome：执行 `npx puppeteer browsers install chrome`。
- 端口被占用：`--start` 固定用 3100、3101、8100；先停掉占用这些端口的进程，或用 `--student-url` / `--teacher-url` / `--backend-url` 对着已有服务跑。
- 老师端账号读不到：确认 `backend/.env` 里有 `ADMIN_PASSWORD`，或显式给 `E2E_ADMIN_USERNAME` / `E2E_ADMIN_PASSWORD`。

## 覆盖边界

- 只跑浏览器版 H5；微信小程序与安卓真机不在本脚本内。
- 文件替换走真实的老师确认接口，不是 mock；因此后端契约不一致会在这里直接暴露。
- 依赖 LibreOffice 的 docx 转换不在链路里，夹具是四份 PDF（1 页与 2 页按不同文件名），避免把转换服务的状态混进前端回归。
- 四文件订单专门覆盖「单文件列放不下」的路径：桌面点「查看全部」看弹窗，手机看卡片逐份列表。
- 上传文件由脚本直接塞给 uni H5 动态创建的 `input[type=file]`：无头浏览器里脚本触发的原生选择框会被判为用户取消，这条替代路径仍然走页面真实的 `/api/file/upload` 与页数读取；多选一次性塞多个路径，走页面自己的多文件上传链路。
- 订单页、详情页、换文件页用「整页刷新」的方式切换：uni H5 会把同一路由的旧页面实例留在栈里，只改查询参数时可能拿到上一单的数据。
- 队列提示（第 42 步）校验的是「页面自己的账」：把接口 `total` 减掉页面当前列出来的条数，必须等于提示里写的隐藏数。页面列出来多少条取决于它这次请求的 `page_size`（轮询按已加载条数、手点查询/刷新 200、「加载更多」+60），所以脚本不写死 60 去算预期，而是记录页面真实请求过的 `page_size` 跟着断言；队列满了 200 条还有单时，提示必须换成「已显示前 200 单（当前显示 200 单）…还有 N 单未显示」并且不再给「加载更多」。
- 第 43 步（保留已加载条数）靠拦截 `/api/admin/queue` 伪造返回：假数据按请求的 `page_size` 造条数（上限 150），请求 60 给 60 条、请求 120 给 120 条。固定返回 60 条的假数据会把「加载更多后条数不缩水」测成恒真，那样这条断言就白写。伪造只影响队列接口，其余请求照常打真实后端，步骤结束会点一次「刷新」回到真实数据。
- 第 43 步最后要再点一次「开始打印」，所以这一步把 `POST /api/admin/order/<id>/start` 也一起伪造成功（假单 id 是 `fake-N`，真后端里没有这些单，不伪造只会报错、页面不刷新，动作之后那条刷新就永远测不到）。假单的 `status` 统一置成 `queuing`、清掉 `files_unconfirmed` / `file_change`：模板单可能已经是「待取件/已完成」，也可能带着「已替换未确认」的拦截标记，原样复制会让这一下根本不发请求。
- 第 43 步的条数是「正好 120 条」而不是「至少 120 条」：页面改回按旧口径拉满 200 条时假数据会返回 150 条，「至少」会把这种错误状态判成通过。
- 第 44 步（封顶提示）不再伪造，直接真造超量数据：复用回归里刚上传的文件（下单宽限期 48 小时），在学生端页面里调 `/api/order/create` 批量下单造到 260 单以上。实测单次 19 ms，390 视口造 210 单耗时 3.7 秒，比伪造一个返回可信得多：页面看到的是真后端、真分页、真 `total`。造出来的单留在本轮专用的库里（学生端没有删除接口），同一库第二次跑到这一步时 `total` 已经够，算出来的待造数是 0，不会重复造。
- 封顶状态只维持到下一拍轮询（轮询按第一屏 60 条拉），所以第 44 步每次手点「刷新」后盯 12 秒找那一瞬，没碰上就再刷一次（最多 3 次），而不是赌一次渲染时机。
- 第 55、56 步（学生端 AI 密钥）依赖另一路的界面；面板不在本分支时这两步跳过并在终端与 `result.json` 里写清楚原因。跳过是显式行为，不是恒真断言：界面合入后同一条路径直接生效。
- 第 56 步的密钥面板按钮一律按面板范围点击（`.key-panel, .ai-key-panel, .key-sheet` 内的按钮）：「我的」页顶上还有一个昵称的「保存」按钮，全局按文字找会点到它。
- 学生端与老师端各打一次生产包（第 45、46 步）：构建要一分多钟，两个视口共用同一份扫描结果。
